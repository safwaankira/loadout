How it works

Everything below lives in HydraDB and is read by graph traversal on every task.

1 · Tools are a graph

Every tool is a node. DEPENDS_ON edges say which tool produces a parameter another one needs.

2 · Plan by traversal

Find the target tools, walk their dependencies up to 3 hops, then drop any branch whose answer is already in memory.

3 · Runs write back

Lookups the run made become Memory nodes with a fresh-until time. A setter (like set_wifi_status) marks its lookup stale.

A vector store can rank tools. It can't tell you that share_location_via_email needs validate_email and get_current_location, or that the location was already fetched 3 minutes ago. Those are edges.

Plug it into your agent

An MCP server with two tools: get_context(task) before a task, report_run(task, results) after it.

{
  "mcpServers": {
    "loadout": { "type": "http", "url": "https://YOUR-HOST/mcp" }
  }
}
Built on HydraDB (open-source engine) through selfgraph's store layer. Tool-graph approach from graph-tool-call. Benchmark: ToolLinkOS (573 tools, 1,569 tasks, MIT). Tool runs in the demo return simulated values.
